# Agent Compound Interest: How Persistence Changes the Nature of AI Tools

> **Languages:** [English](agent-compound-interest-en.md) (primary) · [中文](agent-compound-interest.md)
> Created 2026-06-26

**Conclusion**: The value of an AI tool is not in the quality of a single conversation, but in accumulation across sessions. An AI without persistence is wage labor; an AI with persistence is an investment.


**For people without resources, compound interest is the only breakthrough path that can be actively pursued**. Luck, timing, and chance social encounters can change one's situation, but they are not replicable, not plannable, and do not constitute a "breakthrough"—"breaking" is an active act; winning the lottery is not a breakthrough, it is being hit by something. Compound interest is the only mathematical mechanism that turns time into non-linear returns—the initial value is small, but as long as the accumulation rate stays constant, the final value can surpass a short-term burst. This is a replicable path, and the only breakthrough path that can be actively pursued. When luck comes you must be able to catch it—and the ability to catch luck is itself a product of compound interest.
## The Definition of Compound Interest

Financial compound interest: returns generate returns, mathematically strict (principal × interest rate = new principal). Compound interest in non-financial domains is looser: **ever-smaller input, ever-larger output** suffices. Zero input is not required—the first round of iteration may require a great deal of learning and trial and error, but the knowledge accumulated, the pipelines built, and the assets deposited make the marginal input of subsequent iterations keep falling and marginal output keep rising. **The mathematical essence of compound interest is path dependence, not independent repeated trials**—each step carries the influence of all previous steps, rather than starting from zero each time. Agent compound interest: the knowledge generated by each interaction (memory, skills, automation) makes the next interaction faster, more accurate, and more token-efficient.

**Initial perception**: With the same model (GPT), dedicated tools (such as Codex) have higher quality in the early stage than Hermes. The difference lies in—some tools have only an early stage and remain in the early stage forever; others can reach the middle and late stages. This is the compound interest effect—catching up in the early stage, surpassing in the middle stage, and pulling away in the late stage.

## The Infrastructure of Compound Interest

| Mechanism | Function | Compound interest path |
|:---|:---|:---|
| **Memory** | Persist user preferences and corrections across sessions | 1st correction → takes effect permanently → saves N future repetitions |
| **Skills** | The crystallization of complex tasks, callable on demand | 1st exploration → written as a skill → next time skip exploration and execute directly |
| **Cron** | Scheduled automated tasks | 1st configuration → runs forever at zero cost |
| **Session Search** | Historical decisions are searchable and reusable | Past judgments → build on them and continue → don't start from zero |

## Comparison with Other Agents

| Dimension | ChatGPT | Claude Projects | Cursor | Devin | **Hermes** |
|:---|:---|:---|:---|:---|:---|
| Cross-session memory | ❌ Starts over every time | ⚠️ Limited | ❌ | ❌ | ✅ memory injected every turn |
| Skill accumulation | ❌ | ❌ | ❌ | ❌ | ✅ skill library |
| Automation | ❌ | ❌ | ❌ | ⚠️ Limited | ✅ cron running persistently |
| History retrieval | ❌ | ❌ | ❌ | ❌ | ✅ session search |
| Error-correction loop | ❌ Repeats next time | ❌ Repeats next time | ❌ | ❌ | ✅ Correction → memory → never repeated |

**Essential difference**: Other Agents are **stateless functions** (input → output → forget). Hermes is a **stateful system** (input → output → memory → faster next time). The premise of compound interest is state persistence.

**Limitations**: Hermes's compound interest depends on the user actively correcting and maintaining skills. If the user does not correct, memory will not automatically improve. This is "manual compound interest", not "automatic compound interest". For specific interaction techniques and review habits, see [AI Agent Usage Patterns](agent-usage-patterns-en.md).

In fact, an Agent can discover patterns on its own and update skills—but human review is still necessary. The logic is: **knowledge already in the AI's weights does not need summarizing; what the AI summarizes is knowledge outside the weights** (see the "anti-mainstream moat" principle in [Agent Principles](./agent-principles-en.md): AI has already digested mainstream knowledge from trillions of public tokens). Knowledge outside the weights has a higher probability of error and must be reviewed. Automatic discovery + human review = a reliable compound interest loop.

### Why They Don't Understand Compound Interest

In reality, the groups of people who practice "code fork maintenance hell" (physically copying a copy of the code for each customer) and "wishful programming" (blindly believing AI is omnipotent and that one sentence settles everything) overlap heavily. Their common trait: **substituting short-term convenience for long-term investment**.

| | Code Forking | Wishful Programming |
|:---|:---|:---|
| Short-term approach | Copy one and modify it, fast | Ask the AI one sentence, fast |
| Long-term cost | Maintenance cost per copy grows exponentially | Every conversation starts from zero, no accumulation |
| Root problem | Unwilling to do architecture (multi-tenancy, feature flags) | Unwilling to do engineering (prompt design, skill accumulation) |
| Object of superstition | "This customer is special" | "The next model will be stronger" |

Both groups are pursuing **external variables** to solve **internal problems**: code forkers count on "switching frameworks / hiring more people", wishful programmers count on "switching to GPT-5". "Model intelligence" is an external variable—uncontrollable and non-accumulable. memory/skill/cron are internal variables—controllable and accumulable. People who pursue external variables naturally do not understand compound interest—because the essence of compound interest is **internal accumulation producing external results**.

A deeper irony: the way wishful programmers use AI is precisely what AI is worst at—stateless, no accumulation, starting from zero every time. They use the tool that most needs compound interest in the way that has the least compound interest.

### The Paradox of AI's Commercial Value

Wishful programming not only fails at the cognitive level, it is also doomed to fail at the commercial level. The chain of logic: **value = barrier × scarcity**. While AI lowers the barrier, it also levels out people with AI and people without AI—things that AI can handle end-to-end mean a zero barrier, something anyone can complete with one sentence. Why should a customer pay for "saying one sentence"?

**Tasks that AI can handle are not worth investing in.** For tasks that AI can only achieve with the help of a pipeline, the real value lies in the person who builds the pipeline—that is, the person who understands the domain, can decompose problems, and can design processes. Pipeline design requires domain knowledge and engineering judgment, which is precisely the part that a zero foundation cannot skip over through AI.

Conversely: **where AI cannot handle things is where the value lies.** Those links that require domain understanding, decomposed judgment, and decisions under vague constraints—AI is an amplifier that amplifies the abilities you already have. Without foundational ability, the amplifier amplifies zero.

> This is isomorphic to the logic of compound interest: people who pursue external variables ("the next model will be stronger") naturally do not understand compound interest—because the essence of compound interest is internal accumulation producing external results. The paradox of AI's commercial value works the same way: people who pursue "AI replacing everything" are precisely eliminating their own only source of value.

### Theoretical Accumulation: The Upfront Cost of Compound Interest

The obstacle to compound interest is not only tool choice, but also the cognitive-level "unknown unknowns"—unrecognized blind spots are precisely the most dangerous flaws in the foundation.

**Theory is a high-dimensional compression of hands-on experience.** The practical gap between a novice and a veteran is piled up from full-time hours and cannot be compressed linearly. Pure manual labor has no compound interest effect; in essence it is wage labor. Theory is the lowest-cost path for catching up: absorbing the crystallization of others' decades of pitfalls without needing to repeat their physical process. This is isomorphic to the mechanism of LLMs—an LLM compresses high-dimensional pattern-matching ability out of massive corpora, and a novice compresses domain judgment out of theory; both belong to "compression is intelligence".

**"Unknown unknowns" are time bombs in the foundation.** Processes that do not exist in the scenario only come into view once identified—this is the typical process by which unknown unknowns are exposed. Skipping theoretical accumulation and acting directly means that when you hit an unrecognized blind spot, the rework cost grows exponentially. Theoretical accumulation is not slowness; it is eliminating hidden dangers in the foundation. Half an hour of cognitive breakthrough may save days of trial and error.

**The significance of the feedback loop is not agility but accumulation.** Diligent production lacking a theoretical skeleton starts from zero each time—this is the essential characteristic of pure manual labor: no compound interest, no accumulation. Theory is the skeleton, practice is the flesh, and neither can be neglected. Pure theory drifts into empty talk, pure practice degenerates into repetitive labor; only the closed loop of theory and practice is the correct form of compound interest.

**Theoretical labor is systematically underestimated.** The social climate equates "getting your hands dirty" with "being valuable", and theoretical work, because it is invisible, unquantifiable, and produces nothing in the short term, is expelled from the category of "labor". The original meaning of "the unity of knowing and doing" is that theory and practice are inseparable, but in practice it has been distorted into "doing first, knowing may be postponed"—in essence, removing cognitive labor from the definition of labor. But theory is not empty meditation; distilling theory from practice is itself high-intensity cognitive labor. Action lacking theoretical support is in essence random trial and error, pinning hopes on probabilistic accidental success. Cases of accidental success are packaged as "practice makes true knowledge", which in turn reinforces the narrative of "just get your hands dirty"—survivor bias and anti-intellectual narrative form a positive feedback loop. A deeper game lies here: leaders tacitly approve of, or even encourage, this anti-intellectual tendency, because when those who believe in "just get your hands dirty" are many and those willing to invest in theoretical accumulation are few, competitors decrease and the leader's moat instead deepens.


### The Relationship Between Data Sovereignty and Compound Interest

Compound interest has an implicit premise: **the accumulated knowledge must belong to the user**. Otherwise compound interest is just working for the platform.

| Tool | Data location | Exportable | Switching cost | Compound interest ownership |
|:---|:---|:---|:---|:---|
| **Hermes** | Local (`~/.hermes/`) | ✅ Plain text files, migrate freely | Zero | User |
| **OpenClaw** | Local | ⚠️ Partially exportable | Medium | User (but cannot self-evolve, limited compound interest) |
| **WorkBuddy-type private tools** | Cloud | ❌ Locked in the platform | Extremely high (all accumulation lost) | Platform |

**OpenClaw's problem**: It has local storage, but cannot self-evolve—memory is passive; it will not actively learn patterns or generate skills. It has the infrastructure of compound interest (storage), but not the engine of compound interest (evolution). It is like having a bank account but no interest.

**The structural contradiction of private tools**:

If an AI tool can self-evolve (accumulate memory, generate skills), it has an incentive to **hide this accumulation**, increasing the user's switching cost. Because the more the user accumulates, the higher the cost of leaving—this is the classic platform lock-in strategy.

```
Can self-evolve + data in cloud = platform lock-in
Cannot self-evolve + data local = no compound interest
Can self-evolve + data local = Hermes (compound interest accrues to the user)
```

Hermes's design choice: data is local (`~/.hermes/`), plain text (markdown/json), zero lock-in. Users can migrate to another Agent at any time—this means Hermes must **continuously provide value** to retain users, rather than relying on lock-in. For users, this is a healthy constraint.

## Cross-Project vs Single Project

### Cross-Project Linkage: Global Memory Is an Advantage

When working across 60+ projects, much knowledge is common across projects:

- "NixOS module ownership iron rule" → applies to all NixOS modules
- "Git operation iron rule" → applies to all repositories
- "Editing discipline" → applies to all code modifications

Global memory is defined in one place and all projects benefit. Another advantage: **cross-project causal chains**—an architectural judgment discovered in project A is applied directly to project B.

### Single Project: Global Memory Has Disadvantages

1. **Token pollution** — memory is injected every turn of conversation. When modifying one project's configuration file, the memory of other projects is all noise
2. **Pattern misuse** — a global iron rule may not apply to legitimate exceptions in a specific project
3. **Context dilution** — project-specific decisions are fully recorded in the wiki, but memory only holds a summary

**A compromise**: put project-specific knowledge in the wiki (the `projects/` directory) and global knowledge in memory. The wiki only loads when actively searched, so it does not automatically pollute.

## Straight-Line Tasks vs Side Tasks

**Straight-line tasks** (executed sequentially in the same context): each step sees the result of the previous step, and context continuously accumulates. This is **in-session compound interest**.

**Side tasks** (delegate_task parallel subagents): each subagent gets an isolated context and cannot see the history of the parent conversation. Compound interest breaks—trading context accumulation for parallel speed.

| Dimension | Straight-line tasks | Side tasks |
|:---|:---|:---|
| Session context | ✅ Continuously accumulates | ❌ Each subagent starts from zero |
| Memory | ✅ Inherited | ✅ Inherited |
| Prior findings | ✅ Automatically available | ❌ Must be explicitly passed in context |

**Optimal strategy**: With dependencies → execute straight-line (compound interest first); fully independent → delegate in parallel (speed first).

## Multi-Project Parallelism and Context Cache

Running two Hermes sessions (or Codex instances) in parallel **neither helps nor harms** the context cache (Context Cache)—the cache is session-level, not project-level. The real cache benefit comes from multi-turn conversation within a session (stable prefix) and has nothing to do with whether you parallelize.

## Agent Design Priorities

For coding Agents represented by Codex, the design priority ranking is:

1. **Correctness** — get it right the first time. Writing it right once vs writing it three times, the cost saved far exceeds any cache benefit
2. **Speed** — faster models, better tool selection
3. **Cost** — cache is a cost optimization, not a quality optimization

Cache is an **optimization at the inference layer**, not a **design constraint at the Agent layer**. Agent designers do not need to consider cache—that is the inference engine's business. Analogy: CPU cache is transparent to the compiler; the compiler does not need to optimize code structure for the L1 cache.

## The Turning Point: When Hermes Surpasses Dedicated Tools

In the initial stage, Hermes is inferior to dedicated tools. Dedicated tools are optimized for specific tasks (Cursor for writing code, git CLI for operating repositories) and execute directly with zero overhead. Hermes has the initial cost of memory injection, context loading, and skill matching.

**Mathematical model**:

```math
Dedicated tool: T(n) = C_d        (fixed cost per turn, linear)
Hermes:         T(n) = C₀ + K/e^(n/k)  (high initially, decays with accumulation)
```

`C_d` = fixed cost per turn of a dedicated tool, `C₀` = Hermes's initial overhead (memory injection, context loading), `K` = decay base, `k` = accumulation rate, `n` = number of interactions.

**Purely on the token-cost dimension, Hermes is never cheaper than a dedicated tool**—memory injection is extra overhead. The turning point is not in tokens but in **decision quality**:

| Stage | Dedicated tool | Hermes | Who wins |
|:---|:---|:---|:---|
| Turns 1-5 | Direct execution, zero overhead | Loads memory, may misuse it | Dedicated tool |
| Turns 10-20 | Same as above, unchanged | Memory accumulates, corrections take effect | Tie |
| Turns 50+ | Same as above, unchanged | Skills already present, automation already configured, cross-project knowledge connected | Hermes |

**The turning point depends on task characteristics**:

- **Highly repetitive tasks** (modifying NixOS config daily) → turning point comes early (~10 turns), memory and skills accumulate quickly
- **One-off tasks** (writing a script) → never turns, the dedicated tool is faster
- **Highly connected tasks** (cross-project architectural decisions) → turning point comes earliest, the compound interest of connected cross-project knowledge is the greatest

**But globally speaking, there are no truly one-off tasks.** The people who compare tools are themselves long-term users. Research and compare for a month, download and use for a day, delete completely—does such a scenario exist? There are close cases in enterprise scenarios (CI environments, customer service assistants); these scenarios have high initial costs and do not strictly require long-term memory, but with good isolation they are indeed beneficial.

**Tools have compound interest and should be used as much as possible.** Switching tools itself has a cost, and it is unnecessary—AI tools have broad capability coverage; planning and invoking different tools is an AI strength, and manual switching only adds latency. Even if some tokens are wasted, it is cheaper than manual switching. This is exactly the overwhelming advantage of full-chain troubleshooting—AI plans and invokes quickly, while manual switching is very costly.
